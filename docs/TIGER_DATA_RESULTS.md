## Synthetic rider events

Source of every number in this section: SYNTHETIC rider events (`rider_events.is_synthetic = true`) generated by `data_platform.demo_measure`, not real riders. The stops, routes and scheduled hours they are anchored to are real MBTA static data.

Measured 2026-11-21 on a Tiger Cloud service (0.5 CPU, 2 GiB RAM), PostgreSQL 18.7, TimescaleDB 2.32.1.
Reproduce with `python -m data_platform.demo_measure` from `data-platform/` (fixed seed 0.2026, safe to re-run; `--cleanup` removes the demo rows).

### Data

| Item | Rows |
|---|---|
| `rider_events` (30 days, real MBTA stops/routes, schedule-weighted hours) | 250,000 |
| `points_ledger` (ref_type `demo`) | 125,000 |
| Synthetic users (`demo_0001`..`demo_0500`) | 500 |

Generation took 17 s. Each user has a home route used about 70% of the time.

### Compression (`rider_events`, hypertable with 7-day chunks)

Settings (migration 0008): `compress_segmentby = 'user_id'`, `compress_orderby = 'time DESC, id'`, policy after 7 days. For the measurement every chunk was compressed.

| | Chunks | Table | Indexes | Toast | Total |
|---|---|---|---|---|---|
| Before | 6 | 37.8 MB | 58.1 MB | 0.1 MB | 96.0 MB |
| After | 6 | 2.7 MB | 0.6 MB | 12.9 MB | 16.2 MB |

- Compression ratio on total hypertable size (tables, indexes, toast): **5.9x**.
- `hypertable_compression_stats` (96.0 MB before, 15.9 MB after): **6.0x**.
- Compressing all chunks took 1.6 s.

### Query latency (server-side planning + execution time from `EXPLAIN (ANALYZE)`, median of 5 runs after 1 warm-up, aggregates refreshed first; excludes network round trip)

| Query | Continuous aggregate (ms) | Raw table (ms) | Speedup |
|---|---|---|---|
| Leaderboard, global, last 30 days, top 50 (uncompressed raw) | 129.69 | 104.71 | 0.8x |
| Home line for every user (uncompressed raw) | 264.66 | 396.34 | 1.5x |
| Leaderboard (after compressing `rider_events`) | 49.48 | 79.56 | 1.6x |
| Home line for every user (after compressing `rider_events`) | 220.38 | 183.86 | 0.8x |

The leaderboard reads `points_ledger` (not compressed), so its raw timing does not change with `rider_events` compression. The home-line raw query reads `rider_events`.

### Exact queries

Leaderboard, continuous aggregate (`leaderboard_daily`):

```sql
SELECT * FROM leaderboard('global', 'month', NULL, NULL, 50)
```

Leaderboard, raw table:

```sql
WITH t AS (
        SELECT user_id, sum(delta) FILTER (WHERE delta > 0) AS pts FROM points_ledger
        WHERE at >= time_bucket('1 day', now() - interval '30 days') GROUP BY user_id)
    SELECT (rank() OVER (ORDER BY t.pts DESC NULLS LAST))::int, t.user_id, u.username, t.pts
    FROM t JOIN users u ON u.id = t.user_id ORDER BY 1, u.username LIMIT 50
```

Home line, continuous aggregate (`user_route_daily` behind the `home_line` view, 30 days, at least 5 rides, ties to the most recent line):

```sql
SELECT * FROM home_line
```

Home line, raw table:

```sql
WITH recent AS (
        SELECT user_id, route_id, count(*) AS checkins_30d, max(time) AS last_ride FROM rider_events
        WHERE event_type IN ('checkin', 'ride_start') AND route_id IS NOT NULL
          AND time >= time_bucket('1 day', now() - interval '30 days') GROUP BY user_id, route_id),
    ranked AS (SELECT *, row_number() OVER (PARTITION BY user_id
                                            ORDER BY checkins_30d DESC, last_ride DESC, route_id) AS rn
               FROM recent)
    SELECT user_id, route_id, checkins_30d FROM ranked WHERE rn = 1 AND checkins_30d >= 5
```

### Summary for the pitch

250,000 synthetic rider events (anchored to real MBTA stops, routes and schedule hours) compress 5.9x on total hypertable size. Query timings are reported as measured, with no claim of a continuous-aggregate win: on this small, single-run dataset on a 0.5 CPU service, the aggregate was 0.8x (leaderboard) and 1.5x (home line) relative to raw before compression, and 1.6x and 0.8x after. Timings vary run to run on a shared service; treat speedups near or below 1x as noise at this size. The real-data section has the continuous-aggregate comparison on live MBTA data.

## Real MBTA data

Source of every number in this section: REAL data from the MBTA V3 API (`/vehicles`, `/predictions`, `/alerts`, subway, light rail and bus), collected by `python -m data_platform.collector` into Tiger Data. No synthetic rows are involved. Measured 2026-11-21 on a Tiger Cloud service (0.5 CPU, 2 GiB RAM), TimescaleDB 2.32.1. Reproduce with `python -m data_platform.bench_real` (collector stopped).

### Data (source: MBTA V3 live feed)

| Table | Rows |
|---|---|
| `vehicles` (positions, 2026-11-19 19:37 to 2026-11-21 20:19 UTC) | 53,309 |
| `predictions` | 20,675 |
| `alerts` | 60 |
| `alert_entities` | 265 |
| `vehicles_route_5m` aggregate buckets | 292 |

### Compression (source: `hypertable_detailed_size` total, tables + indexes + toast; every chunk compressed for this measurement)

| Hypertable | Size before | Size after | Ratio (total size) | Ratio (`hypertable_compression_stats`) |
|---|---|---|---|---|
| `vehicles` | 156.2 MB | 41.4 MB | 3.8x | 138.5x |
| `predictions` | 15.2 MB | 2.6 MB | 6.0x | 29.0x |

"Before" is the size when the benchmark started: chunks older than 1 day were already compressed by the policy, the newest were not. After, every chunk is compressed. The stats ratio covers compressed chunks only.

### Query latency: vehicle position reports per line per 5 minutes, last 3 days (source: `EXPLAIN (ANALYZE)` server-side planning + execution, median of 5 after 1 warm-up)

| State | Continuous aggregate `vehicles_route_5m` (ms) | Raw `vehicles` (ms) | Speedup |
|---|---|---|---|
| Before forced compression | 1.56 | 98.0 | 62.82x |
| After compression | 1.97 | 74.85 | 37.99x |

Aggregate query:

```sql
SELECT l.id AS line_id, c.bucket, sum(c.reports) AS reports
    FROM vehicles_route_5m c JOIN routes r ON r.id = c.route_id JOIN lines l ON l.id = r.line_id
    WHERE c.bucket >= now() - interval '3 days'
    GROUP BY l.id, c.bucket ORDER BY l.id, c.bucket
```

Raw query:

```sql
SELECT l.id AS line_id, time_bucket('5 minutes', v.time) AS bucket, count(*) AS reports
    FROM vehicles v JOIN routes r ON r.id = v.route_id JOIN lines l ON l.id = r.line_id
    WHERE v.time >= now() - interval '3 days'
    GROUP BY l.id, time_bucket('5 minutes', v.time) ORDER BY l.id, bucket
```

The dataset is only a few days of polling, so it is small for TimescaleDB; results at this size may not reflect larger volumes.
